# audio-sync

多台设备分段上传短音频及元数据，服务端校验并建立**可靠时间索引**。不做语音识别，
不做音频生成（仅模拟设备产生测试音）。纯 Python 标准库实现，无第三方依赖。

```
python3 run_server.py --port 8077        # 启动（状态在 ./data，重启即恢复）
python3 demo_scenario.py                 # 可选：自动演示完整剧情
python3 -m unittest discover -s tests    # 测试
打开 http://127.0.0.1:8077/              # 控制页面
```

## 系统组成

| 模块 | 职责 |
|---|---|
| `audiosync/devicesim.py` | 设备模拟：按墙钟节拍采集小段正弦音，分块上传；模拟丢块/损坏/重复/冲突/离线补传/换采样率/重启清零 |
| `audiosync/app.py` | HTTP API：可续传的分块上传、设备控制、校验与索引查询、静态页面 |
| `audiosync/validator.py` | 独立校验线程：WAV 解析、PCM 校验和、元数据一致性；支持撤回/重新校验 |
| `audiosync/indexer.py` | 独立索引线程：构建 + CAS 发布，只发布自洽版本 |
| `audiosync/core.py` | 索引领域逻辑：epoch 划分、对齐、覆盖/缺段、冲突、无法确认区间 |
| `audiosync/storage.py` | SQLite 持久化（WAL），进程重启后原样恢复 |

上传协议（`segment_uid` 幂等，块位图续传）：
`POST /api/upload/start` → `POST /api/upload/chunk?session_id&index`（二进制）
→ `POST /api/upload/complete`。会话与块持久化在 SQLite，**进程重启后上传原样继续**；
设备端状态（计数器、run_id、离线积压）也持久化，重启后继续原接收与补传。

## 为什么不能把文件时长相加当覆盖

片段会重叠、重复、缺失。覆盖一律按 **counter 区间并集** 计算：
同一 epoch 内所有已校验片段的 `[counter_start, counter_start+nsamples)` 求并，
再经对齐映射到服务器时间轴求并。重复段（同区间同内容）去重计数，
重叠段只算一次，缺段是并集在已知范围内的补集。

## 设备样本计数 ↔ 接收时间：对齐方式

每个设备按 **epoch**（一次"计数生命"）对齐，epoch 内按采样率切成 **rate run**
（换采样率不清计数器，所以每个速率段需要自己的映射）。

- **锚点**：只有"活的"片段可用——上传完成时间 ≈ 采集结束 + 有界传输延迟
  （滞后超过 2s 的片段判定为补传，不作锚点）。锚点取
  `x = counter_end, y = completed_at`。
- **速率锁定拟合**（发布用）：斜率固定 `1/rate`，`offset = median(y - x/rate)`，
  对离群稳健；再做一遍 MAD 离群剔除后重拟合（迟到的"活"片段、队列排空段
  会被剔除并计数报告 `n_outliers`）。
- **自由线性拟合**（对照用）：最小二乘斜率+截距，斜率偏离 `1/rate` 即
  **时钟漂移** `drift_ppm`。只有 ≥3 个锚点才估计（两点恒能连线，漂移无意义），
  且仅当漂移既统计显著（>3 倍斜率标准误）又足够大（>5000ppm）才判降级，
  否则短窗口噪声会不停误报。
- **换采样率**：无锚点的速率段尝试从上一段**链式续接**（计数器连续假设），
  标 `chained` 并加宽误差；无法续接的标 `unanchored`——counter 区间已知，
  服务器时间映射未知。
- **补传段**：不参与拟合，经 epoch 映射落位，并用设备时钟交叉核对
  （`captured_at` 隐含的 offset 与拟合相差 >1s → `clock-disagreement`）。

## 误差与无法确认的区间

每个映射区间带 `err`（拟合残差 max 与 0.25s 网络抖动下限的较大者；链式段再加 1s）。
以下区间显式列入 `unconfirmable`，页面单独展示：

| 原因 | 含义 |
|---|---|
| `counter-reset-boundary` | 计数器清零的 epoch 边界：样本计数无法跨边界链接，只有接收时间可用 |
| `unanchored-run` | 整段速率区间无活锚点且无法续接（如纯补传开局） |
| `chained-alignment` | 无活锚点，靠计数器连续假设从上段链接，误差加宽 |
| `degraded-alignment` | 残差/漂移超阈（上传滞后不稳定等），映射带宽误差 |
| `clock-disagreement` | 补传段的设备时钟与 epoch 拟合矛盾 |
| `conflict` | 同 counter 区间出现不同内容，整组排除出覆盖，等待人工处理 |

计数器重置的检测：按 `(captured_at, counter_start)` 排序遍历，run_id 变化
或片段整个落在当前 epoch 最小计数之前 → 新 epoch。用采集时间排序是为了
让迟到的补传不被误判成重置。已知盲区：若重置前后两段生命 counter 都从 0
开始且内容不可区分，只能按重复/冲突处理——这本身列为无法确认的情形。

## 校验与索引分离、撤回、自洽发布

- 校验（线程 A）与索引（线程 B）完全分离；片段状态机
  `pending → validated | rejected`，`validated → retracted`。
- 每次校验状态变更与 `validation_version++` 在**同一事务**提交。
- 索引构建读 V 时刻快照 → 构建 → 仅当 `validation_version` 仍为 V 才
  CAS 发布；否则丢弃重建。因此**撤回立即生效**：旧索引不会被继续统计坏片段；
  **重建与补传并发**时只发布自洽版本（UI 可见 builds/discarded_builds 计数）。
- 已发布索引不可变，历史版本可查询（审计），统计只来自当前发布版。

## 进程恢复

全部状态在 `./data`（SQLite + WAV 文件）。杀掉 `run_server.py` 再启动：

- 未完成的上传会话保留块位图，设备用同一 `segment_uid` 重开会话续传；
- `pending` 片段启动时重新入队校验；
- 设备线程按持久化的配置/计数器/积压队列复活，继续采集与补传；
- 索引按恢复后的校验状态重建并发布。

## 页面

`/` 控制页：设备启停、改配置（采样率/段长/块大小/丢块/损坏/重复/冲突/离线率）、
重启清零；覆盖时间线（绿=覆盖，红=缺段，黄=无法确认，紫=冲突）；缺段表；
无法确认区间表；对齐报告（每速率段的锚点数/offset/漂移/残差/置信）；
索引版本与来源（每段的 counter 区间→映射时间→误差→是否锚点）；
片段表（状态徽章 + 撤回/重新校验）。

## 已知限制（演示规模）

- 校验/索引是进程内线程，设备很多时应拆为独立进程/队列；当前规模下
  校验可能短暂滞后（pending 积压），重启或空闲后自愈，一致性不受影响。
- 对齐质量取决于上传滞后的稳定性；滞后斜坡会体现为漂移并把该速率段
  判为降级——这是有意为之的保守行为。
- 设备时钟不可信时（`clock-disagreement` 频发）应只信接收时间锚点。
